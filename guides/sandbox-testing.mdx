Use the sandbox to validate your integration without moving funds. Test and Live credentials, routes, and records are isolated.

## Route and key isolation

| Environment | Route prefix | API key prefix |
| --- | --- | --- |
| Test | `/v1/sandbox` | `txk_test_` |
| Live | `/v1` | `txk_live_` |

A Test key sent to `/v1/*` is rejected with `400`. A Live key sent to `/v1/sandbox/*` is also rejected with `400`.

<Warning>
Do not use `X-Transika-Environment` to select an API-key environment. The request path and key prefix are authoritative.
</Warning>

## Authentication and access

Sandbox access does not bypass merchant controls for normal accounts:

- KYB/KYC must be `approved`.
- Live mode, live API keys, and live webhooks additionally require ops **Enable Live** (`liveEnabled`).
- `otc` is required for tGHS.
- `api_access` is required for webhook endpoint management.
- API keys use only `api:read` and `api:write`; `api:write` implies read.
- The request source must match the Test key's IP whitelist.

**Test Partners** (ops-provisioned) are a shortcut for sandbox demos:

- Created with KYB approved, `otc` + `api_access` granted, and Live permanently locked.
- Dashboard login is email + password only (`otpRequired: false` — no OTP email).
- Ops provisions login, an optional webhook URL, and a `txk_test_` key (secrets shown once).
- Live traffic and Enable Live return `403`/`422` with `errors.code: "test_partner_live_forbidden"`.

If KYB/KYC is not approved, product routes return `403` with `errors.code: "kyb_required"`. If Live is not enabled, Live `/v1` traffic and live key/webhook creation return `403` with `errors.code: "live_access_required"`. If a feature is missing, gated routes return `403` with `errors.code: "feature_not_entitled"`. A non-whitelisted source returns `403` with `errors.code: "api_key_ip_not_allowed"`.

## Configure a test client

Keep the base URL and key outside source code.

```bash
export TRANSIKA_API_URL="https://sbx-institutional.tran-sika.com"
export TRANSIKA_TEST_API_KEY="txk_test_REPLACE_LOCALLY"

curl "$TRANSIKA_API_URL/v1/sandbox/tghs" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY"
```

Never send a Test key to a Live route or reuse test webhook secrets in Live.

## Data isolation

The following data is scoped to the selected environment:

- Ghana beneficiaries
- tGHS balances, activity, and payout requests
- Webhook endpoints and deliveries
- Dashboard OTC trades (not part of this public API)

IDs from one environment should be treated as unavailable in the other. For example, a Test beneficiary cannot be used with a Live payout.

## Test tGHS

Acquire Test tGHS balance through the Transika dashboard when needed, then read the authoritative summary:

```bash
curl "$TRANSIKA_API_URL/v1/sandbox/tghs" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY"
```

Confirm `data.wallet.explorerUrl` for on-chain proof of the managed wallet. You can test a beneficiary payout with:

```bash
curl -X POST "$TRANSIKA_API_URL/v1/sandbox/tghs/payout" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 10000,
    "beneficiaryId": "d64cb955-01c7-4a10-b1bf-1479ebb6fa9f",
    "reference": "INV-10000-9460",
    "idempotencyKey": "payout-inv-10000-9460-1",
    "simulateFailure": true
  }'
```

`simulateFailure` lets you verify failure handling in Test. Create returns
`approved` and the burn runs on the background worker — run `npm run dev:worker`
(or set `ENABLE_BACKGROUND_JOBS=true`) locally so Test burns advance to
`burn_submitted`. After the request, poll `/tghs/redemptions?reference=…` or
listen for `tghs.payout.*` webhooks until terminal. Retrying with the same
`idempotencyKey` should return the existing payout instead of creating another debit.

A successful Test payout (without `simulateFailure`) returns an activity with your `paymentReference`, a terminal `succeeded` or `failed` status, refreshed balance, and an `explorerTxUrl` when a ledger transaction hash exists. Look the row up again with `GET /tghs/activities?reference=INV-10000-9460` or `GET /transactions?reference=INV-10000-9460`.

## Test webhooks

Create an endpoint with `"environment": "test"` through the sandbox route, then call:

```bash
curl -X POST \
  "$TRANSIKA_API_URL/v1/sandbox/webhooks/endpoints/$ENDPOINT_ID/test" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY"
```

The receiver gets a signed `webhook.test` payload. Test endpoints also receive Test `tghs.payout.*` events when you run sandbox payouts. They do not receive Live events.

See [Webhooks](/guides/webhooks) for signature verification and retry behavior.

## Before going live

1. Create separate Live API keys with the minimum required scope and production egress IPs.
2. Recreate beneficiaries needed in Live — call Live `POST /beneficiaries/resolve` first so `accountName` is the rail-registered holder name, not a Test simulated name.
3. Register separate Live webhook endpoints and store their new signing secrets.
4. Confirm required product features and KYB/KYC remain approved.
5. Confirm your application uses the Live route prefix and never sends Test credentials to Live.
6. Run a controlled Live transaction and verify your reconciliation and webhook handling.

<Warning>
Sandbox success confirms your integration logic only. It does not confirm that a Live resolve, transfer, or payout will succeed.
</Warning>
