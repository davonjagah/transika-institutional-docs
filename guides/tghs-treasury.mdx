tGHS is a managed treasury balance denominated in Ghana cedis. You can acquire tGHS through an eligible OTC trade, read your available balance and activity, and pay Ghana mobile money or bank beneficiaries.

<Info>
tGHS uses the `otc` feature entitlement. Your merchant must have approved KYB/KYC, and API keys use `api:read` or `api:write`.
</Info>

## How the workflow fits together

<Steps>
  <Step title="Request managed tGHS settlement">
    Create a `crypto_to_fiat` OTC trade with `settleMode: "managed_tghs"`. Accept the quote and submit the stablecoin funding transaction hash.
  </Step>
  <Step title="Wait for settlement">
    Track the trade until its status is `settled`. The quoted GHS amount then becomes available in your tGHS balance.
  </Step>
  <Step title="Create a Ghana beneficiary">
    Store a mobile money or bank beneficiary in the same environment as the balance.
  </Step>
  <Step title="Initiate a payout">
    Submit the beneficiary and amount. In Live, the request automatically
    submits the burn through your managed wallet. Track the redemption until
    its on-chain burn is confirmed.
  </Step>
</Steps>

Transika manages the settlement process behind this workflow; your integration uses only the merchant endpoints documented here.

## Read your balance

```bash
curl "$TRANSIKA_API_URL/sandbox/v1/tghs" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY"
```

The response includes the asset, environment, available balance, and activity counts. Treat the returned balance as authoritative for the selected environment.

## Read treasury activity

```python
import os
import requests

response = requests.get(
    f"{os.environ['TRANSIKA_API_URL']}/sandbox/v1/tghs/activities",
    headers={"Authorization": f"Bearer {os.environ['TRANSIKA_TEST_API_KEY']}"},
    params={"kind": "payout", "status": "succeeded", "page": 1, "limit": 20},
)
response.raise_for_status()
print(response.json())
```

Activity kinds are:

- `mint`: tGHS added through a settled OTC trade.
- `payout`: tGHS used for a beneficiary payout.

Activity statuses are:

- `pending`: processing has not reached a final result.
- `succeeded`: the balance credit or payout completed.
- `failed`: processing failed. Read the current balance before deciding whether to retry.

## Pay a beneficiary

Create the Ghana beneficiary in the same environment before initiating the payout.

```bash
curl -X POST "$TRANSIKA_API_URL/sandbox/v1/tghs/payout" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 250,
    "beneficiaryId": "BENEFICIARY_ID"
  }'
```

The request must not exceed your available balance. A successful request
returns a payout or redemption record for the selected environment.

<Warning>
Live redemption processing temporarily stops at `burn_confirmed`. The confirmed
on-chain burn does not initiate a Ghana payout while the payout rail is
unavailable.
</Warning>

You can also read Live payout-request history:

```bash
curl "$TRANSIKA_API_URL/v1/tghs/redemptions" \
  -H "Authorization: Bearer $TRANSIKA_LIVE_API_KEY"
```

Use `GET /v1/tghs/redemptions/{id}` for the complete receipt. The receipt
includes merchant-visible lifecycle timestamps, the burn transaction hash, and
a `burnExplorerUrl` for the correct Base network once the burn is confirmed.
Provider-specific processing references remain internal. Receipt screens also use
`POST /v1/tghs/redemptions/{id}/refresh` as a safe reconciliation fallback;
this polls the existing Circle transaction and cannot submit another burn.

See [Beneficiaries](/guides/beneficiaries) for supported Ghana account types and network discovery.

<Warning>
Payout requests do not currently accept an idempotency key. If a request times out after submission, check activity and payout-request history before retrying.
</Warning>

## Endpoints

| Method | Endpoint | Scope |
| --- | --- | --- |
| `GET` | `/v1/tghs` | `api:read` |
| `GET` | `/v1/tghs/activities` | `api:read` |
| `GET` | `/v1/tghs/redemptions` | `api:read` |
| `GET` | `/v1/tghs/redemptions/{id}` | `api:read` |
| `POST` | `/v1/tghs/redemptions/{id}/refresh` | `api:read` |
| `POST` | `/v1/tghs/payout` | `api:write` |

Use `/sandbox/v1/tghs*` with a Test API key.

## Environment behavior

Test and Live balances, beneficiaries, activities, payout requests, and linked OTC trades are isolated. Test lets you exercise the workflow without moving funds. Live requests can move value and should be submitted only after you have verified the beneficiary, amount, and environment.
