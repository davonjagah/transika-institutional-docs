tGHS is a managed, GHS-denominated treasury balance held in Transika custody.
In Live it is an on-chain claim in your managed wallet (non-transferable outside
Transika redemption); in Test it is a simulated ledger balance. Acquire tGHS
through the Transika dashboard (OTC desk), then use this API to read your
balance, reconcile on-chain proof links, and redeem to Ghana mobile money or
bank beneficiaries.

<Info>
tGHS uses the `otc` feature entitlement. Your merchant must have approved KYB/KYC, and API keys use `api:read` or `api:write`.
</Info>

## How the workflow fits together

<Steps>
  <Step title="Acquire managed tGHS in the dashboard">
    Complete an eligible OTC trade in the Transika dashboard with managed tGHS settlement. OTC create, accept, funding, and desk simulation are dashboard-only and are not part of this merchant API.
  </Step>
  <Step title="Confirm your balance and wallet">
    Call `GET /v1/tghs` for the authoritative balance and the managed wallet's Base explorer URL.
  </Step>
  <Step title="Create a Ghana beneficiary">
    Store a mobile money or bank beneficiary in the same environment as the balance.
  </Step>
  <Step title="Initiate a payout">
    Submit `beneficiaryId`, `amount`, `reference`, `idempotencyKey`, and optionally `sender` and `metadata`. Transika burns tGHS (real on-chain in Live; simulated with a BaseScan-style proof in Test), then disburses GHS to the beneficiary.
  </Step>
  <Step title="Track status with your reference or receipt id">
    Poll `GET /tghs/redemptions` or `GET /tghs/redemptions/{id}` (and optionally `POST .../refresh`) until `completed` or a terminal failure. Environment is the only switch between Test and Live.
  </Step>
  <Step title="Reconcile with a period statement">
    Use `GET /statements?from=&to=` (or **Transactions → Account statements** in
    the dashboard) for credit/debit/reversal lines with opening and closing
    balances. Export CSV, Excel, or PDF via `GET /statements/export`.
  </Step>
</Steps>

## Read your balance

```bash
curl "$TRANSIKA_API_URL/v1/sandbox/tghs" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY"
```

Example response:

```json
{
  "status": "success",
  "message": "success",
  "data": {
    "asset": "tGHS",
    "environment": "test",
    "balance": "46550.00",
    "wallet": {
      "address": "0x5e31676da4527b910fa1799635d0291ee2727a00",
      "network": "base",
      "explorerUrl": "https://basescan.org/address/0x5e31676da4527b910fa1799635d0291ee2727a00",
      "onchainRegistered": true
    },
    "activityCounts": {
      "mint": 9,
      "payout": 7,
      "failed": 1
    }
  }
}
```

Treat the returned balance as authoritative for the selected environment. Amounts and balances are decimal strings with exactly **2** fractional digits (e.g. `"10000.00"`). Requests may include at most 2 decimal places.

### On-chain proof of balance

| Source | Field | What it proves |
| --- | --- | --- |
| `GET /tghs` | `data.wallet.explorerUrl` | Managed wallet address on Base |
| `GET /tghs` | `data.wallet.address` | Same address, for your own explorer lookup |
| Redemption | `burnExplorerUrl` + `burnTxHash` | Burn proof for the payout (real in Live; simulated BaseScan link in Test) |

`wallet.onchainRegistered` indicates whether the managed address is registered for on-chain balance checks in the selected environment.

## Merchant reference and status lookup

Pass your internal correlation id as required `reference` on `POST /v1/tghs/payout` (max 64 characters). Transika stores it, returns it for reconciliation, and uses it as rail narration. Pair it with a required `idempotencyKey` (8–64 chars) so retries return the existing redemption instead of creating a duplicate.

Look up payouts with `GET /tghs/redemptions?reference=INV-1042` or `GET /tghs/redemptions/{id}` in **both** Test and Live. For both the list filter and the path param, matching is exact on any of:

- your `reference`
- the redemption `id`
- `idempotencyKey`
- `transaction.transactionId`

`POST /tghs/redemptions/{id}/refresh` accepts the same lookup values.

## Read treasury activity (mints)

`GET /tghs/activities` lists mint ledger rows for the selected environment. **Payouts** use redemption receipts (`/tghs/redemptions`), not activities.

```python
import os
import requests

response = requests.get(
    f"{os.environ['TRANSIKA_API_URL']}/v1/sandbox/tghs/activities",
    headers={"Authorization": f"Bearer {os.environ['TRANSIKA_TEST_API_KEY']}"},
    params={"kind": "mint", "status": "succeeded", "page": 1, "limit": 20},
)
response.raise_for_status()
print(response.json())
```

Activity kinds:

- `mint`: tGHS added through a settled OTC trade (dashboard).
- `payout`: legacy Test ledger payouts only (new payouts are redemptions).

## Pay a beneficiary

Create the Ghana beneficiary in the same environment before initiating the payout. The same `POST /tghs/payout` and `/tghs/redemptions*` URLs work in Test and Live — environment (API key / header) is the switch. Test simulates burn + BaseScan proof; Live uses the real chain.

```bash
curl -X POST "$TRANSIKA_API_URL/v1/sandbox/tghs/payout" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 10000,
    "beneficiaryId": "d64cb955-01c7-4a10-b1bf-1479ebb6fa9f",
    "reference": "INV-10000-9460",
    "idempotencyKey": "payout-inv-10000-9460-1",
    "sender": {
      "fullName": "Ama Mensah",
      "idType": "passport",
      "idNumber": "G1234567",
      "purpose": "family_support"
    }
  }'
```

| Field | Required | Notes |
| --- | --- | --- |
| `amount` | Yes | At most 2 decimal places; must not exceed available balance |
| `beneficiaryId` | Yes | Same environment as the balance |
| `reference` | Yes | Your correlation id (max 64). Returned as `reference` on the redemption. Used as rail narration. |
| `idempotencyKey` | Yes | Retry key (8–64 chars). Same merchant + environment + key returns the existing redemption. |
| `sender` | No | Remitter: `fullName` (required when block present, or both `firstName` and `lastName`), optional `idType` + `idNumber`, `transactionType`, `remittance`, `currency`, `amount`, `purpose` |
| `beneficiary` | — | Not returned on GET. Snapshot stored internally for BOG reporting. |
| `senderProvided` | GET only | `true` when remitter KYC was captured on create |
| `metadata` | No | Optional string map (max 20 keys). |
| `simulateFailure` | No | Test only. Simulated burn succeeds; Ghana payout fails. Balance is not restored after burn. |

## Payout lifecycle

`POST /v1/tghs/payout` creates a redemption in both environments.

```text
approved → burn_submitted → burn_confirmed → payout_pending → completed
                 ↘ burn_failed                 ↘ payout_failed
```

| Status | Meaning |
| --- | --- |
| `approved` | Request accepted; burn submission is queued on the worker |
| `burn_submitted` | Burn submitted (real in Live; simulated BaseScan proof in Test) |
| `burn_confirmed` | Burn confirmed; Ghana payout is starting |
| `payout_pending` | Ghana disbursement is in progress |
| `completed` | Beneficiary payout succeeded |
| `burn_failed` | Terminal — burn failed; Ghana never sent; balance not reduced ([details](/guides/tghs-payout-failures)) |
| `payout_failed` | Terminal — burn succeeded; Ghana not delivered after rail exhaustion; safe to refund your customer ([details](/guides/tghs-payout-failures)) |

Create returns `approved` and enqueues the burn. Listen for `tghs.payout.burn_submitted` (or poll / `refresh`) until terminal:

```bash
curl -X POST "$TRANSIKA_API_URL/v1/sandbox/tghs/payout" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 168000,
    "beneficiaryId": "6cd84483-4088-4579-a2e1-1d872ea3e22e",
    "reference": "INV-168000",
    "idempotencyKey": "payout-inv-168000-1"
  }'

curl "$TRANSIKA_API_URL/v1/sandbox/tghs/redemptions?reference=INV-168000" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY"

curl -X POST "$TRANSIKA_API_URL/v1/sandbox/tghs/redemptions/9ce685a9-5886-4de6-871a-041bdb95f592/refresh" \
  -H "Authorization: Bearer $TRANSIKA_TEST_API_KEY"
```

Example completed receipt:

`POST /v1/tghs/redemptions/{id}/refresh` re-checks burn status and resumes payout if needed. It does not submit another burn.

Provider-specific processing references remain internal. Merchant receipts expose business status, your `reference`, beneficiary snapshot fields, burn proof, and lifecycle timestamps.

After a payout reaches `completed`, Transika submits the applicable regulatory
report separately. Transika tracks that submission by its reporting event ID
until the reporting service confirms final `sent` status. This internal
reporting lifecycle does not change the merchant payout receipt from
`completed` or require you to poll another endpoint.

## Endpoints

| Method | Endpoint | Scope |
| --- | --- | --- |
| `GET` | `/v1/tghs` | `api:read` |
| `GET` | `/v1/tghs/activities` | `api:read` |
| `GET` | `/v1/tghs/redemptions` | `api:read` |
| `GET` | `/v1/tghs/redemptions/{id}` | `api:read` |
| `POST` | `/v1/tghs/redemptions/{id}/refresh` | `api:read` |
| `POST` | `/v1/tghs/payout` | `api:write` |

Use `/v1/sandbox/tghs*` with a Test API key.

## Environment behavior

Test and Live balances, beneficiaries, payout requests (redemptions), and linked OTC settlements are isolated. Test is a full Live rehearsal (same URLs, simulated burn/BaseScan, same webhooks) without moving real funds. Live requests can move value and should be submitted only after you have verified the beneficiary, amount, and environment.
